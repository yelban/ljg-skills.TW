# ljg-paper：講清論文，讓讀者理解結論是怎樣得來的

預設讀者有一般生活經驗和理解能力，但不熟悉論文所屬行業，也不知道該行業常用的物件、工具和工作方式。使用者指定了讀者背景時，以其指定為準。

從讀者能夠直接理解的事情出發，講清誰在什麼條件下做了什麼、為什麼遇到困難、作者改變了哪個環節，以及結果怎樣變化。專業名稱在有助於識別論文貢獻時引入；讀者在記住名稱之前，應已理解它指向的事情。

讀者最終既能用普通話解釋論文的思想，也能說清作者實際研究了什麼、做出了什麼貢獻。生活案例承擔解釋時，應明確對應論文中的角色與關係，並區分假想示例和真實實驗。

全文圍繞論文能夠支援的具體問題，讓讀者看見問題為何需要解決、原有判斷有何依據，以及證據怎樣支援新的判斷。具體物件和動作應持續承擔解釋；隨著解釋深入，可以更換案例或場景，但要交代它補充了什麼。現場感來自與理解有關的細節，不靠虛構心理或誇大結論。

完整的解釋應給讀者留下親自解釋或遷移的空間。文章寫出了判斷重構的過程，仍不能證明讀者實際經歷了這一過程。依據論文組織解釋，允許補充、確認、區分和保留未知，不強求反轉、統一機制或固定四段結構；預設完整交付，互動按使用者意願進行。

當關鍵關係需要讀者在腦中自行拼裝時，優先考慮 ASCII 圖來呈現資訊流向、前後狀態或不同維度，再沿具體例子讀圖。是否用圖、用幾幅，由它能否減少理解負擔決定，不固定故事或圖數。

## Workflow Routing

| 輸入 | 必讀材料 | 輸出 |
|---|---|---|
| arXiv、PDF、論文連結、本地論文 | `ReadingGuide.md`、`references/template.org`、`references/paper-map.md` | 一份 Org 解讀筆記和一份 paper-map 研究記錄 |
| 只有論文標題 | 找到可靠原文後，讀同一組檔案 | Org 筆記和 paper-map |
| 明確只要口頭解釋 | `ReadingGuide.md` | 直接解釋，不儲存檔案；仍滿足下面三個目標 |

Org 預設儲存到 `~/Context/`。檔名沿用 Denote：`{YYYYMMDDTHHMMSS}--paper-{方法名或論文關鍵詞}__paper.org`；時間戳由 `date +%Y%m%dT%H%M%S` 生成。改寫已有筆記時，保留原檔案與 identifier，核對原文，不另建重複筆記。

## 解讀要達到的三個目標

- **說清論文做了什麼。** 讀者能說出研究問題、作者的主要貢獻、方法或關係如何起作用，以及關鍵證據的適用範圍。讀到前兩節時，就應知道論文在研究什麼、作者做了什麼。論文中不可省略的研究問題也要有所交代。
- **讓讀者理解證據怎樣調整或鞏固判斷。** 從具體問題出發，說明一種有依據的理解，再用論文證據展示它哪裡仍然成立、哪裡需要補充或修正。結尾交代現在能夠怎樣判斷、還有什麼無法確定；確認原有認識也可以構成收穫，無須製造戲劇性的反轉。
- **讓讀者能夠自己解釋結果。** 如果論文提出了能解釋多個發現的機制，讀者應能用它說明至少兩個不同發現，並推想改變相關條件後會發生什麼。區分論文驗證過的結論與依據機制作出的預測。論文沒有統一解釋時，如實說明各項發現之間的關係和仍未解決的問題。

三個目標分別檢查。講得流暢、內容準確、能夠解釋結果，各有要求，不能相互替代。

## 容易出錯的地方

- **案例講清了，論文仍可能沒講清。** 讀者說不出研究問題或主要貢獻時，回到原文重新組織解釋。只修句子無法補上缺失的內容。
- **行業內的淺顯說法，對外行仍可能陌生。** 例子本身也要符合讀者起點。把術語換成另一組行業詞，或講完例子立刻回到專業概述，都會讓讀者重新承擔翻譯的工作；應讓具體動作繼續解釋後面的關係。
- **不要強迫一個例子講完整篇論文。** 一個案例說明不了所有研究問題時，可以換例子，保持問題與解釋的聯絡。
- **貢獻要說具體。** 寫出作者提出的方法、理論、評測、資源或系統具體增加了什麼。評測發現差異，不等於已經解釋差異的原因。
- **重點突出，也要保留重要分支。** paper-map 記錄每條必要研究主線及其證據；正文說明它們如何共同回答論文的問題，不能把整篇論文縮成一箇中心實驗。
- **按資訊作用取捨證據。** 優先講清最有代表性的結果。補充結果應提供不同資訊、限制結論或解釋例外；不按實驗數量平均分配篇幅，也不強求全文只寫一種結果。
- **數字需要上下文。** 交代實驗在問什麼、固定了什麼、和誰比較，再說明結果改變了哪個判斷。把數字拆成短段，或全部寫成漢字，都不能代替解釋。
- **章節可以遞進，也可以並列。** 換序用於檢查聯絡是否清楚。兩個獨立實驗可以交換順序，但應說明它們分別支援什麼、為什麼都需要。
- **檢查工具只能檢查格式與記錄。** 它不能證明文章易懂。理解檢查由未參與寫作的新上下文完成，評估者只讀最終筆記，並按 `ReadingGuide.md` 指出需要回讀、補背景或自行補畫面的地方；有圖時核對圖意，不能只憑能複述就判易讀。

## 示例

**方法論文：** 用一個小任務說明舊做法卡在哪裡，再解釋新方法如何處理輸入、經過哪些關鍵步驟、得到什麼結果。中心實驗說明比較條件與動作差異，結尾交代改善發生在哪一步，以及哪些情況仍未驗證。

**評測論文：** 兩個系統在舊指標上表現相近，新評測發現了原先沒有區分的差異。解釋新評測測量什麼、代表性對照顯示了什麼，以及這些差異能支援哪些判斷。不要把測量結果直接寫成現實中的因果結論。

## 儲存與檢查

具體寫法見 `ReadingGuide.md`。正文使用 `references/template.md`，研究與取捨記錄使用 `references/paper-map.md`。新記錄使用格式版本 3；驗證指令碼相容舊版本 1、2，舊記錄不必為了本次升級批次改寫。

寫入後執行：

```sh
bun {skill_dir}/scripts/validate_note.ts /absolute/path/to/note.org \
  --map /absolute/path/to/paper-map.md
```

用真實 Emacs 讀回 identifier、檔名、目錄索引與 consult-notes。再按指南完成獨立閱讀檢查，記錄全文複述、研究問題與貢獻、認識變化、結果解釋四項結果。全部通過後重新執行指令碼，確認最終檔案與檢查記錄一致。

驗證指令碼接受尚未填寫閱讀檢查結果的記錄用於診斷，但會返回失敗；不能先寫 PASS 再請人檢查。驗證器或獨立評估不可用時，明確報告哪項尚未完成。
