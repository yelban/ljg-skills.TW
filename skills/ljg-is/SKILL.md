# 把一個名詞講到能用

只給定義，讀者可能記住了詞，卻仍不知道怎樣認出它。只講動詞，讀者又可能知道它做了什麼，卻不清楚它究竟是哪一類東西、邊界在哪裡。

`ljg-is` 把兩者接起來：名詞回答「它是什麼」，讓概念在認知地圖裡站穩；動詞回答「它怎樣起作用」，讓概念在現實裡動起來。真正完成的理解還要繼續走一步：它改寫了讀者原來的什麼判斷，下次遇到它時又能怎樣行動。

```text
它是什麼，和什麼不一樣？
它靠什麼動作產生結果？
知道這一點後，我不再怎樣想？
下次遇到它，我先看什麼、怎樣做？
```

這四個問題是一條理解路徑，不是四個正文欄目。文章要像一個人順著疑惑把事情講明白，而不是把答案依次填進表格。

趙汀陽的「動詞」思想在這裡仍然重要，但它是一副有條件的透鏡。面對制度、平臺、角色或規範，可以繼續追問誰選擇了這種做法，它怎樣改變參與者；面對目標函式、遞迴這類技術概念，動詞首先是物件自身的運算與作用。材料沒有顯示社會反制，就不把技術說明硬拽成制度批判。

## 成品標準

一篇合格解讀會讓讀者發生四個連續變化：

- 能用一句普通話說出 X 屬於什麼，以及它與最容易混淆的物件差在哪裡。定義要給邊界，不能只給比喻或用途。

- 能順著一個真例項子說明 X 怎樣起作用。技術概念講清輸入、關鍵動作和結果；制度概念講清參與者、規則怎樣進入行動以及實際後果。只寫物件真正具有的機制。

- 能指出自己原來哪種看法需要修改。認知變化必須由前面的定義和機制推出，不另起爐灶追求「深刻」。

- 能在一個具體情境裡使用這番理解。行動指導要說清先看什麼、怎樣判斷、何時調整，並能解釋為什麼。

正文從一個普通讀者真的會有的疑惑、誤解或使用場景進入，不強制編造人物故事。概念要儘早出現，例子負責驗證解釋，不負責製造戲劇性。

最後可以落在一句判斷、一個行動原則或一個真實未決問題上。哪一種自然，由前文決定；問號不是深度證明。

預設寫入：

```text
~/Context/{時間戳}--理解-{目標片段}__is.org
```

新成品使用 `ljg-is-v5` schema。正文使用兩到四個隨內容生出的標題和四到十個自然段，不把「是什麼 / 怎樣運作 / 認知改變 / 行動指導」直接用作四個欄目。

## 判斷邊界

- **定義與理解不同。** 使用者若只要形式化定義、公式證明或術語翻譯，直接回答即可；只有當他想理解概念如何工作、意味著什麼或怎樣使用時，才進入本技能。

- **動詞不等於社會創制。** 技術物件可以通過計算、對映、比較、壓縮或遞迴起作用，不必虛構一個創造者故事。制度物件才追問選擇者、規則與反作用。

- **行動指導不是操作手冊。** 本技能給判斷抓手，不替代某個軟體、流程或行業的逐步教程。

- **理由不能偽造。** 區分材料支援的事實和分析者的推斷。不知道就縮小判斷，不替人物補寫動機，也不把一般機制冒充具體案例事實。

## Gotchas

- **不要把新合同寫成新清單。** 「定義、機制、啟發、建議」若各佔一欄，文章仍然生硬。它們應當像一條推理：因為 X 是這樣運作的，所以原來的判斷不夠準確，下一次才應當這樣做。

- **不要只給用途當定義。** 「目標函式用來最佳化」沒有說明它是什麼；要補上它怎樣給候選方案建立可比較關係，讀者才可能把它與約束、指標或獎勵區分開。

- **不要強制具體場景。** 一個真實疑惑往往比虛構工程師或司機更自然。只有當人物行動確實承載機制時才使用故事。

- **不要強造趙汀陽式轉折。** 未選可能、反制、本源和未來不是必填項。它們只有能解釋物件，並且有現實根據時才進入正文。

- **不要在結尾突然升級尺度。** 前文講演算法，結尾忽然質問社會正義，通常不是深刻，而是換了問題。認知改變與行動指導必須能夠逐句追溯到已經講清的機制。

- **不要給萬能建議。** 「保持關注」「綜合考慮」「具體問題具體分析」刪除概念名後仍然成立，說明它沒有使用前文的理解。

- **不要讓元資料替正文說話。** `definition`、`operation`、`recognition` 與 `guidance` 是後臺索引；正文可以用更自然的說法，但全文讀回必須找到同一內容。

## Examples

**目標函式**

```text
不要寫：目標函式是最佳化的靈魂，它最終會反過來支配設計者。
可以寫：目標函式是一把供求解過程比較方案的尺子。它給每個候選方案一個
可比較的結果，讓程式知道往哪邊改進。因此看到「最優」時，先補問一句：
這是按照哪把尺子得到的最優？
```

**績效考核**

```text
先講清：它是組織定期判斷工作表現並連線後續決定的一套正式做法。
再講它怎樣通過指標、敘述或評議進入獎金與機會。由此自然推出：考核不只
記錄工作，也會改變人們接下來選擇什麼工作；設計考核時要檢查它正在獎勵的
行為，而不能只檢查表格是否完整。
```

**邊界案例**

```text
User: 請給出遞迴函式的形式化定義並證明這個定理。
→ 不呼叫 ljg-is；這是形式定義與證明任務。

User: 我知道遞迴是自己呼叫自己，但還是不懂它到底是什麼，寫程式時怎麼判斷該不該用？
→ 呼叫 ljg-is；這需要把定義、運作方式、認知修正與使用判斷接起來。
```
