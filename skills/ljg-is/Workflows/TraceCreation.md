# UnderstandInUse Workflow

把一個「X 是什麼」的問題寫成可使用的理解。成品既讓讀者認清 X 的概念位置，也看見它怎樣運作；隨後從這套機制中自然推出認知修正與行動判斷。

## 理想成品

一個不瞭解框架的讀者讀完後，能夠用自己的話完成四件事：把 X 與相鄰概念區分開，說明 X 怎樣產生結果，指出這番理解改變了自己原來的哪個判斷，並在真實情境中用它作一次更好的選擇。

文章只有一條理解路徑。定義讓物件站穩，機制讓物件動起來，認知變化說明前兩者為何重要，行動指導把新的判斷帶回現實。後一部分必須使用前一部分已經建立的理解，不能並列交卷。

## 後臺理解，前臺講解

寫作前先在後臺把五件事想清楚：

- **定義。** X 屬於哪一類東西，靠什麼特徵與最近的相鄰概念分開。形式物件可以給形式定義，但仍要翻成普通話。

- **運作。** 什麼進入 X，X 做了什麼，什麼因此改變。技術物件常表現為輸入、關鍵操作與結果；制度物件常表現為參與者、規則與後果。

- **認知修正。** 普通人最容易把 X 誤解成什麼。定義和機制講清以後，哪種舊判斷已經不能繼續保留。

- **行動判斷。** 在什麼真實情境中，這番理解會改變讀者下一步。要檢查什麼訊號，怎樣選擇，什麼時候說明需要調整。

- **根據與邊界。** 哪些是材料或一般機制支援的事實，哪些只是推斷，什麼情況會使當前解釋失效。

這五件事是分析者的準備，不是正文目錄。正文不使用「定義、運作、認知改變、行動指導、根據、邊界」等欄位式標題，也不把它們換成近義詞繼續逐項填寫。

趙汀陽的問題鏈只作條件性補充。若 X 是制度、平臺、角色或規範，再檢查誰把哪種做法穩定下來、其他可能是什麼、反覆使用怎樣改變參與者。若這些問題對物件沒有真實解釋力，就留在後臺，不為了哲學完整而寫進文章。

前臺沿著讀者的理解變化展開：

- 從一個真實疑惑、常見誤解或實際使用情境開始。人物場景可以用，但不強制虛構主人公。

- 儘早給出普通話定義，並馬上用相鄰概念或反例劃出邊界。讀者先知道在談什麼，後文才不會懸空。

- 用一個夠近的例子把運作過程走一遍。例子必須對應定義裡的關鍵關係，不能只負責熱鬧。

- 從機制推出認知修正。明確說明原來的哪種看法為什麼不夠準確，不突然換到更宏大的社會問題。

- 把新判斷放進真實決策。指導讀者先看什麼、怎樣判斷和何時調整，並說明這與前述機制的關係。

- 根據內容自然收束。可以是一句更準確的判斷、一條行動原則，也可以是材料真正留下的未決問題。

標題隨內容生長，段落數量可以伸縮。完成初稿後刪掉機制段再讀行動指導：若指導仍然完全成立，它就是沒有使用 X 的萬能建議。再檢查最後的轉折：若刪掉前文仍能成立，便應刪除或重寫，而不是靠問號保留。

## 普通話合同

- 概念名儘早出現。不要為了敘事感讓讀者走很久才知道文章在解釋什麼。

- 定義先說上位類別和關鍵差別，再用例子落地。比喻可以幫助理解，但不能代替邊界。

- 一句話推動一個主要變化。連續三個以上抽象名詞、過多頓號或分號，通常說明後臺清單洩漏到了前臺。

- 每段兩到四句。段落之間可以是概念遞進、因果推進或判斷修正，不必偽裝成時間故事。

- 少用「首先、其次、此外、綜上」。它們只標示排列，不會製造因果和時間。

- 不追求思想腔。能說「一把用來比較方案的尺子」，就不先說「可計算的價值秩序」。

一個不瞭解框架的讀者若不能回答「它是什麼—它怎麼工作—我以後怎麼用」，成品就沒有完成。

## 根據合同

輸入附帶檔案、書、文章、URL 或對話材料時，先讀取原材料。沒有材料時，只使用物件的一般定義與執行條件，並自然說明沒有核驗哪些具體實現或案例事實。

`basis` 記錄成品直接依賴的事實根據。由此推出但材料沒有直接說明的判斷，要在正文中用「這意味著」「由此可以推斷」等自然說法標明。傳聞、感覺和未經核驗的可能性不能寫成根據。

## Markdown 輸出合同

複製技能根目錄的 `Template.org`，生成：

```text
~/Context/{時間戳}--理解-{目標片段}__is.org
```

- 時間戳使用 `date +%Y%m%dT%H%M%S`；可讀時間使用 `date "+%Y-%m-%d %a %H:%M"`。

- 目標片段保留 4–24 個有意義字元；不足四字時增加真正說明主題的詞，不用無意義填充。

- schema 固定為 `ljg-is-v5`，tags 同時包含 `is` 與 `act`。

- `definition` 用普通話記錄 X 的上位類別與關鍵差別。

- `operation` 記錄 X 怎樣起作用以及什麼因此改變。

- `recognition` 記錄這番理解修正了哪種舊判斷。

- `guidance` 記錄面對 X 時可執行的觀察、判斷或選擇。

- `basis` 簡要記錄事實基礎，不寫推斷和傳聞。

- `falsifier` 在後臺記錄什麼事實會推翻當前解釋；正文只在理解需要時自然處理，不強塞進最後一段。

- 正文使用兩到四個隨內容生出的一級標題，全文通常四到十段；正文不使用專案符號或欄位標籤。

- 結尾由內容決定，可以是判斷、原則或真問題，不要求問號。

除非使用者明確說「只分析」「不落盤」或 `read-only`，否則儲存到 `~/Context`。

## 驗收合同

儲存後執行：

```bash
bun ~/.agents/skills/ljg-is/Tools/ValidateNote.ts "<Markdown 檔案路徑>"
```

驗證器通過後仍要全文讀回。機械檢查只能確認理解骨架存在，不能證明中文已經自然。讀回時做四次測試：

1. **名詞測試：** 能否一句話區分 X 與最容易混淆的物件？

2. **動詞測試：** 能否不照抄定義，講清 X 怎樣讓輸入、選擇或關係發生變化？

3. **認知測試：** 能否說出「原來我以為……，現在我知道……」？

4. **行動測試：** 能否舉出一個下次會改變觀察或選擇的具體情境？若刪掉機制段，建議仍然完全成立，說明它只是萬能建議。

另外單獨檢查結尾：它是否只是為了顯得深刻而突然提高尺度。若轉折沒有被前面的定義與機制逼出來，就刪除，不補一個更響亮的問題。

最終對話用兩三段自然中文交付定義、最重要的認知變化與行動抓手，再給檔案路徑與驗證結果。不要把 Markdown 的後臺檢查重新複製成聊天列表。

## 失敗邊界

- 找不到能區分相鄰概念的定義：說明還沒有真正回答「是什麼」，先縮小物件或補材料。

- 找不到可複述的運作過程：說明只給了標籤或用途，沒有形成理解。

- 找不到由機制推出的認知修正：不要另造哲學轉折，寧可保持樸素。

- 行動指導刪除概念名後仍適用於任何事：它是空話，回到機制重寫。

- 趙汀陽問題鏈在物件上找不到現實支點：只保留物件自身的運作，不偽造創造者、反制或未來。

- 校驗通過但普通讀者仍覺得拗口或轉折不成立：以讀者反饋為最終反證，重建全文路徑，不做區域性換詞。
